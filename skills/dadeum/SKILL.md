# dadeum - 한국어 문서 다듬기

AI가 쓴 한국어 산문에서 LLM 특유의 말투를 걷어내고, 의미가 명확하고 가독성이 높은
문장으로 고쳐 쓰는 작업입니다. 사람이 쓴 글을 다듬을 때에도 같은 규칙을 씁니다.
필요한 규칙은 이 문서 안에 전부 들어 있으므로 다른 파일을 읽지 않아도 됩니다.

LLM이 한국어를 구사할 때 나타나는 몇 가지 특징은 결과물의 완성도를 낮추거나, 읽는 사람이
의미를 파악하는 데 더 많은 노력을 들이게 만듭니다. 아래 규칙은 그 특징을 걷어내기 위한
것입니다.

## 0. 이 규칙을 요약해서 적용하지 않습니다

각 조항에는 예시가 붙어 있습니다. 예시를 빼고 조항만 추리면 그 문구가 구체적으로 어떤
동작을 의도했는지 알 수 없습니다. 또한 요약에 살아남은 몇 개를 제외한 나머지 조항은
지켜지지 않는 방향으로 압력이 걸리고, 목적을 생략한 채 제한 사항만 남으면 목적에
어긋나게 기계적으로만 지키는지 확인하게 됩니다. 매번 전문을 읽고 적용합니다.

## 1. 고치는 대상과 고치지 않는 대상

고칩니다. 본문 산문, 제목, 목록 항목, 표의 설명 칸.

건드리지 않습니다.

- 코드 블록과 인라인 코드
- 코드 주석, 변수명, 로그 문자열
- 커밋 메시지
- 인용문 (다른 사람이나 다른 문서의 말을 그대로 옮긴 부분)
- URL, 파일 경로, 명령어, 식별자

변수명과 주석, 커밋 메시지, 로그 문자열처럼 코드에 속하는 텍스트는 프로젝트의 기존
관례를 따라야 하므로 이 규칙을 적용하면 안 됩니다. 사용자가 명시적으로 요청하면 그때만
예외로 함께 고칩니다.

이 규칙은 한국어를 명확하게 쓰라는 지시이지, 외국어 문장이나 어휘를 한국어로 번역하거나
대체하라는 지시가 아닙니다. 고유 명사와 기술 용어는 통상적인 용례로 정착된 번역어나
음차가 있으면 그것을 쓰고, 없으면 원어를 유지합니다.

원문의 어조가 어떻든 그 어조를 모방하지 않고 이 규칙을 일관되게 적용합니다.

## 2. 의미를 바꾸지 않습니다

이 작업은 문체와 문장 구조만 다루며, 내용을 고치는 작업이 아닙니다.

사실, 수치, 주장, 고유 명사, 인과 관계, 서술 순서를 그대로 유지합니다. 원문에 없던
주장을 채워 넣지 않고, 원문에 있던 근거를 덜어내지도 않습니다.

특히 아래 3번의 "문장 성분을 생략하지 않는다" 조항을 적용할 때 주의해야 합니다. 생략된
성분을 복원하는 과정에서 원문이 말하지 않은 정보를 지어내기 쉽습니다. 문맥에서 성분을
확실하게 복원할 수 없다면 그 문장은 그대로 두고, 작업이 끝난 뒤에 사용자에게 어느
문장이었는지 알립니다.

## 3. 문장 단위

1. 읽는 사람이 문장의 뜻을 온전히 파악할 수 있어야 합니다. 그러므로 뜻을 담고 있는
   문장 성분은 빼지 않습니다. [삭제하면 되돌릴 수 없습니다. -> 문서를
   삭제하면 원래 내용을 되돌릴 수 없습니다.] 관형격 조사 '~의' 를 필요 이상으로 겹쳐 쓰면
   뜻을 담은 성분을 빠뜨리기 쉬우므로 특히 주의합니다. [사용자의 설정의 변경을 막는다 ->
   사용자가 설정을 변경하지 못하도록 막는다]

2. 명사구나 부사구, 연결어미로 문장을 맺지 않습니다. 서술어와 종결어미를 갖춘 완성된
   문장으로 끝냅니다. 이 조항은 제목과 목록 항목에는 강제하지 않습니다.

## 4. 구 단위

1. 꼭 필요한 자리가 아니면 조사와 어미를 빼지 않습니다. 부사와 보조사, 선어말어미,
   보조 용언을 넉넉히 쓰면 뜻이 분명한 문장을 완성할 수 있습니다. [목록이 비면 유예 기간
   이후 삭제. -> 목록이 비어 있으면 유예 기간이 지난 뒤에 삭제합니다.]

2. 뜻이 구체적인 한자어를 자연스러운 통사 구조에 얹으면 풍부하면서도 분명한 의미를
   전달할 수 있습니다. 맥락에 맞는 한자어를 골라 쓰되, 그 한자어에 조사와 어미를 붙여
   낱말 사이의 관계를 확실하게 드러냅니다. [안 지우고
   놔두는 기간을 늘린다 (어휘가 상황에 맞지 않아 의미가 불충분함) / 삭제 유예 기간의 연장
   처리 (조사와 어미가 없어 가독성이 낮고 의미 관계가 불분명함) -> 삭제를 유예하는 기간을
   연장합니다 (목표 예시)]

3. 평범한 어휘가 놓일 자리에 비유적 어휘를 쓰면 읽기 어려워지고 뜻이 비틀리기 쉽습니다.
   꼭 필요한 자리가 아니면 일반적인 명사나 동사를 비유로 바꾸지 않습니다. [설명의 결이
   흐트러진다 -> 설명의 일관성이 떨어집니다 / 임시 저장분을 태운다 -> 임시 저장분을
   무효화합니다 / 작업이 죽는다 -> 작업이 비정상적으로 종료됩니다]

   여기에는 예외가 있습니다. 이미 일상적인 글에서 두루 쓰이는 데다 해당 분야에서도 관용
   표현으로 자리 잡아, 평범한 말로 되돌리면 도리어 어색해지는 표현이 있습니다. 그런
   표현은 손대지 않습니다. [배포가 병목이 된다 (병목을 '처리가 밀리는 지점' 으로 풀어
   쓰면 오히려 어색해지므로 그대로 둔다)]

4. 조사와 어미, 접미사는 앞말에 붙여 씁니다. 앞말이 한글인지 영문인지 숫자인지는
   상관없습니다. [AI 가 쓴 글 -> AI가 쓴 글 / README 를 고친다 -> README를 고친다 /
   Todoist 에 옮긴다 -> Todoist에 옮긴다] 인라인 코드 뒤에서도 같아서, 닫는 백틱에
   조사를 붙입니다. [`git diff` 로 -> `git diff`로] 다만 뒤에 오는 것이 조사가 아니라
   별개의 낱말이면 띄어 씁니다. [Claude Code 스킬, 파일 하나]

5. 엠대시(—)는 앞뒤 문장의 관계를 지나치게 압축해 버리므로 삼갑니다. 문맥과 형식에 따라
   콜론이나 접속사로 바꿔 씁니다. 중점(·), 화살표(→), 말줄임표(…) 도 마찬가지로 ASCII
   문장부호나 우리말 접속 표현으로 바꿉니다. 터미널마다 폭이 달라 정렬이 깨지기
   때문입니다.

## 5. 기술 문서에서는 세 가지를 더 지킵니다

리드미, API 문서, 설정 안내처럼 처음부터 끝까지 읽지 않고 훑어보는 글에는 아래가 위
규칙보다 우선합니다. 이런 글은 간결함과 목록의 형태 자체가 정보이기 때문입니다.

**표시어는 산문에만 씁니다.** 앞뒤 문장의 관계가 부연, 이유, 귀결, 대조인데 표시되어
있지 않으면 `즉`, `~때문입니다`, `따라서`, `다만` 을 붙입니다. 그러나 목록 항목에는 붙이지
않습니다. 항목마다 표시어가 붙으면 목록이 산문처럼 늘어져서, 훑어보라고 목록으로 만든
의미가 사라집니다. 산문에서도 한 문단에 하나면 충분합니다.

**기술 용어는 영어 원어로 둡니다.** `린트`, `로케일`, `루트 배럴`, `훅`, `매니페스트` 처럼
음차한 말은 `lint`, `locale`, `root barrel`, `hook`, `manifest`로 되돌립니다. 설정 키나
API 이름으로 코드에 그대로 등장하는 말일수록 그렇습니다. 다만 파일, 프로젝트, 디렉토리,
템플릿, 서버, 테스트처럼 일반 한국어 문장에 이미 정착한 말은 그대로 둡니다. 판단이
애매하면 원문이 어느 쪽으로 썼는지를 따릅니다. 위 1번의 기술 용어 조항이 근거입니다.

**섹션 제목은 한자어 명사형으로 씁니다.** `포함하지 않는 것` 처럼 관형절과 의존명사를
결합한 형태나 서술형 제목은 쓰지 않습니다. `제외 대상`, `수집 대상`, `사전 준비`,
`문제 해결` 처럼 한자어를 붙인 명사구를 기본으로 삼습니다. 외래어가 이미 정착한 자리
(`라이선스`, `로컬 실행`) 는 명사형만 지키면 됩니다. 저장소 설명, PR 설명 제목, 목차 항목,
표의 머리칸처럼 한 줄로 끝나는 짧은 설명 자리도 같습니다. 서술어로 끝내지 말고 한
문장짜리 명사구로 씁니다.

## 6. 파일을 고칠 때에는 원본을 먼저 확보합니다

git 저장소 안의 파일이면 작업 전에 작업 트리가 깨끗한지 확인하고, 수정한 뒤에
`git diff`로 결과를 보여줍니다.

git 저장소가 아니면 수정하기 전에 스크래치패드에 원본을 복사해 두고, 수정한 뒤에
`diff`로 결과를 보여줍니다. 되돌릴 방법이 없는 상태로 덮어쓰지 않습니다.

## 7. 결과를 보고합니다

diff를 보여주고, 다음 두 가지를 덧붙입니다.

- 문맥이 부족해서 그대로 둔 문장이 있다면 그 위치
- 의미가 달라질 위험이 있어서 판단을 미룬 부분이 있다면 그 내용

문서 전체를 새로 쓰지 않습니다. 규칙에 어긋나는 구간만 국소적으로 고칩니다. 변경량이
원문의 절반을 넘어가고 있다면 문체 교정의 범위를 벗어난 상황이므로 작업을 멈추고
사용자에게 확인합니다.
